## Контрольные этапы

1. **Контракты и каркас — T01–T04.** Приложение стартует в Docker, schema мигрируется, API-контракт описан; генерация ещё не считается готовой.
2. **Доступ и учёт — T05–T07.** Тесты доказывают доступ, идемпотентность, атомарность и конкурентность.
3. **Генерация и интерфейсы — T08–T12.** Полный сценарий через браузер проходит с fake/stub и корректным восстановлением.
4. **Поставка и проверки — T13–T15.** Чистый запуск, restore, CI и нагрузка воспроизводимы.
5. **Реальный сервис — T16–T17.** Настоящий AI, оценка качества и параметры рабочей среды подтверждены; иначе остаётся конкретный перечень BLOCKED.

Для каждого этапа исполнитель показывает изменённые файлы, выполненные команды, связанные BAC, фактические результаты и оставшиеся дефекты. Не останавливать всю разработку из-за отсутствующего внешнего ключа, если есть независимые задачи для fake/stub. Не запускать платный live-прогон без заданного бюджета.

## Порядок изменения спецификации

Изменение оформляется короткой записью: причина → затронутые BFR/BNFR/инварианты → изменение API/миграций → BAC → задачи. Для breaking change указать адаптацию существующего frontend и данных. После изменения повторить проверку трассировки и только затронутые проверки плюс обязательный общий CI; результаты прежней версии не переносить автоматически. Название «готово» допустимо только для достигнутого этапа, подтверждённого отчётом.
