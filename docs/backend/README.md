# Спецификация backend для реализации AI-агентами

Пакет описывает создание backend «Мини-Кадрики» и подключение существующего React-интерфейса. Результат реализации — приложение в Docker Compose с Django, PostgreSQL, настоящей AI-генерацией, безопасным учётом единиц и воспроизводимыми проверками.

Дата: 26.11.2026. Версия: 1.0. Статус: спецификация к реализации; backend и Docker-конфигурация этим пакетом ещё не реализованы. AI-агенты выступают исполнителями разработки. Мультиагентная система внутри приложения не требуется.

| Документ | Назначение |
| --- | --- |
| [spec.md](spec.md) | Объём, пользовательские истории, нормативные требования, API и критерий готовности. |
| [plan.md](plan.md) | Архитектура, транзакции, Docker, конфигурация и эксплуатация. |
| [acceptance.md](acceptance.md) | Проверяемые сценарии, трассировка требований, условия сдачи и формат доказательств. |
| [tasks.md](tasks.md) | Порядок реализации, зависимости задач и готовое задание AI-агенту. |

Читать в порядке таблицы. Сначала уточняется спецификация, затем план, затем задачи, код и доказательства приёмки. Такая структура соответствует подходу [GitHub Spec Kit](https://github.com/github/spec-kit/blob/main/spec-driven.md); устанавливать Spec Kit для выполнения задания необязательно.

## Приоритет документов

Этот пакет задаёт целевую реализацию backend. При расхождении внутри пакета `spec.md` определяет поведение, `acceptance.md` — его проверку, `plan.md` — способ реализации, `tasks.md` — порядок работы. Конфликт между ними нужно исправить до реализации затронутой задачи, сохранив требование и критерий проверки согласованными.

Предыдущие [требования](../product/requirements.md), [правила](../product/business-rules.md), [API](../architecture/api-contracts.md), [модель данных](../architecture/data-model.md) и [критерии](../testing/acceptance-criteria.md) остаются контекстом и источником идентификаторов FR/BR/AC. Новые критерии имеют префикс BAC и не заменяют результаты проверок прототипа.

В пакете явно уточнены прежние открытые решения: числовые пределы, таймауты, пагинация, HTTP-контракты, тестовая нагрузка и Docker. Это проектные значения для первой реализации, а не уже согласованные эксплуатационные SLA. Условия подключения реального провайдера и рабочего размещения перечислены в `spec.md`.

## Правила для исполнителя

1. Не менять бизнес-правила ради удобства реализации или прохождения теста. Изменение поведения начинается с изменения спецификации и соответствующего критерия.
2. Не использовать локальное демо, SQLite или мок провайдера как доказательство работоспособности PostgreSQL и настоящего AI.
3. Реализовывать вертикальные этапы из `tasks.md`; завершение этапа подтверждать командами и результатами из `acceptance.md`.
4. Не добавлять очередь, платежи, регистрацию, агентные фреймворки или дополнительные сервисы без изменения объёма.
5. Помечать непроведённую проверку `NOT RUN` или `BLOCKED` с причиной. Отсутствие ключа AI не является успешной проверкой реального провайдера.
6. Фиксировать зависимости и версии образов, хранить секреты вне Git, не переносить демо-пароли в рабочую среду.
