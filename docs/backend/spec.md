# Требования к backend Мини-Кадрики

## Цель и границы

Создать backend для существующего React-приложения: активный пользователь входит, получает стихотворение через внешний AI API, видит свою историю и расход единиц; оператор управляет аккаунтами и начислениями через Django Admin. Приложение и проверки запускаются в Docker без установленного на хосте Python, Node.js или PostgreSQL.

Слова «должен» и «обязательно» обозначают условия приёмки. Все требования BFR и BNFR обязательны для MVP. P1/P2 ниже задают порядок реализации, а не право исключить функцию. Спецификация охватывает backend, контейнеризацию и необходимые изменения HTTP-интеграции frontend. Переработка дизайна не входит в объём.

Вне объёма: самостоятельная регистрация и восстановление пароля, реальные платежи, подписки, дробные единицы, возврат по художественному качеству, пользовательская отмена генерации, стриминг, очередь задач, Redis/Celery, RAG, инструменты для модели, несколько AI-агентов во время исполнения, Kubernetes и автоматическое развёртывание на внешнем хостинге.

## Исходная база и принятые значения

Основа: FR-001–FR-014, BR-001–BR-020 и AC-001–AC-028 существующей документации. Backend: Python, Django, Django REST Framework и PostgreSQL. Один внешний OpenAI-совместимый API, один вызов на принятую генерацию, синхронное выполнение. Внутренние единицы не равны деньгам или токенам провайдера.

| Параметр | Значение первой реализации |
| --- | --- |
| Начальный баланс | 0, без автоматического приветственного начисления. |
| Цена | 10 целых единиц; конфигурация сервера, снимок цены в генерации. |
| Максимум баланса и суммы операции | `MAX_UNITS = 1_000_000_000`; сумма начисления 1…MAX_UNITS с дополнительной проверкой запаса для возвратов. |
| Длительность сессии | Абсолютные 12 часов с момента входа, без продления каждым запросом. |
| Предел ожидания провайдера | 45 секунд на весь вызов, соединение не более 5 секунд; автоматических повторов нет. |
| Просроченная генерация | `deadline_at = started_at + 90 секунд`. |
| Размер тела API | Не более 16 KiB для JSON-запросов; превышение — 413. |
| Размер результата | Не более 16 000 символов и 64 KiB; больший результат считается технической ошибкой. |
| Лимиты входа | 5 неуспешных попыток за 5 минут на нормализованный email и 30 на IP; следующий запрос — 429 с Retry-After. |
| Лимиты новой генерации | 6 принятых запросов за скользящую минуту на пользователя; не более 2 PROCESSING на пользователя и 8 глобально. |
| Постраничная выдача | По умолчанию 20, допустимый `limit` 1…100. |
| Часовой пояс | Хранение и API — UTC; операторские даты и границы дней — Europe/Moscow. |

Числовые значения — решения этой версии спецификации. Изменять их можно через конфигурацию с проверкой диапазонов и соответствующими тестами. Цена обязана быть положительной и не превышать MAX_UNITS. Таймауты должны сохранять порядок из `plan.md`.

Для начала разработки достаточно этих значений и fake-провайдера. Для полной приёмки нужен выбранный реальный endpoint/model, предоставленный серверу ключ, лимит расходов на испытание и доступная тестовая среда. Для рабочего запуска дополнительно нужны домен/TLS, ответственный оператор, политика хранения пользовательских текстов и резервных копий, расписание копирования и согласованные RPO/RTO. Эти внешние решения не блокируют локальную реализацию и не подменяются догадками агента.

### Роли оператора

Права назначаются группами Django; наличие is_staff само по себе не разрешает финансовые действия. Создание операторов и изменение групп/permissions/is_staff/is_superuser доступно только суперпользователю. Пользовательский менеджер не может повысить свои права или создать привилегированный аккаунт, в том числе поддельным POST.

| Роль | Разрешённые действия |
| --- | --- |
| Пользователь | Только собственный пользовательский API. |
| Аудитор | Просмотр пользователей, генераций, кошельков, журнала и итогов в Admin. |
| Менеджер пользователей | Права аудитора; создание обычного пользователя, смена его пароля и блокировка; без управления другими операторами. |
| Оператор начислений | Права аудитора и отдельное разрешение `billing.credit_wallet`; без смены баланса напрямую. |
| Суперпользователь | Управление ролями и разрешёнными операциями Admin; также не может редактировать/удалять финансовую историю через приложение. |

Группы менеджера и оператора начислений можно объединить одному человеку. Суперпользователь приложения не является суперпользователем PostgreSQL.

## Инварианты учёта и состояний

1. У каждого пользователя ровно один кошелёк. `0 <= balance <= MAX_UNITS`; `balance = SUM(transaction.amount)` за всё время.
2. CREDIT > 0, DEBIT < 0, REFUND > 0. Начальный баланс 0 не создаёт фиктивную нулевую операцию.
3. У каждой принятой генерации ровно один DEBIT `-cost`; у FAILED ровно один REFUND `+cost`; у COMPLETED возврата нет. Существование результата без оплаченной генерации запрещено.
4. `balance_after` соответствует состоянию кошелька сразу после конкретной операции. Порядок журнала задаётся `sequence`, а не только временем.
5. На кошельке поддерживается запас: `balance + SUM(cost для PROCESSING) <= MAX_UNITS`. Начисление проверяет это выражение под блокировкой кошелька. Благодаря этому возврат ранее списанной суммы не может переполнить баланс.
6. Переход только `PROCESSING → COMPLETED` либо `PROCESSING → FAILED`. PENDING не используется backend. Финальные состояния неизменяемы. Прикладное удаление аккаунтов с историей, генераций, кошельков и операций запрещено.
7. COMPLETED: непустой валидный result, `completed_at`, отсутствие error. FAILED: result=null, безопасные error_code/error_message, `completed_at` и возврат. PROCESSING: result/error/completed_at=null.
8. Повтор принятого ключа проверяется до текущего баланса, лимитов новых генераций и доступности провайдера. Он должен работать и при балансе 0, и после истечения rate limit. Авторизация и валидация формата обязательны всегда.
9. Ошибки до принятия — без Generation, DEBIT и AI-вызова. Повтор не принятого requestId позднее может быть принят. Принятые ключи хранятся вместе с историей без автоматического TTL.
10. Нет гарантии exactly-once для внешнего провайдера при аварии сети. Приложение не делает автоматический повтор вызова после неопределённого исхода; восстановление только завершает запись с возвратом. Расход у провайдера может сохраниться.
11. Если исход commit неизвестен, сервер сначала перечитывает состояние через рабочее соединение. Без подтверждения нельзя сообщать об успешной генерации или возврате. При недоступной БД ответ 503; дальнейшее восстановление — по ключу и recovery.

## Валидация входных данных

`requestId` — UUID v4. `topic` — строка после Unicode NFC и trim длиной 1…120 Unicode code points. `instructions` — обязательная строка (может быть пустой), NFC, CRLF→LF, trim, максимум 1000 code points. `mood` — `neutral | romantic | cheerful | sad | philosophical | dark`. `stanzaCount` — JSON number, математически целое 1…4; строки, bool, null и дроби запрещены. Недопустимые управляющие символы запрещены, в instructions допустимы LF и TAB. Неизвестные поля отклоняются.

Для сравнения повторов используются нормализованные topic/instructions/mood/stanzaCount; порядок JSON-полей не важен. Цена и текущая модель в сравнение не входят: повтор возвращает исходную запись. Сохраняется версия нормализации; после обновления сервера существующие ключи сравниваются по прежней версии.

Email: trim, нижний регистр целиком, стандартная проверка email, максимум 254 символа; уникальность нормализованного значения обеспечивается БД. Display name: trim, 1…150 символов. Пароли проверяются стандартными валидаторами Django, минимальная длина 12; не хранятся и не логируются открытым текстом. Комментарий начисления после trim — 1…500 символов. Суммы имеют те же строгие правила JSON-чисел; отрицательные, ноль, дроби и переполнение отклоняются без округления.

## Контракт HTTP API

Префикс `/api/v1`, JSON UTF-8, camelCase, UUID строкой, timestamps RFC 3339 UTC с `Z`. Пути ниже без завершающего slash; POST не перенаправляется для исправления slash. Сессия — cookie, никогда не токен в JSON/LocalStorage. Защищённые запросы без активной сессии дают 401 JSON. `GET /auth/me` — исключение: 200 null для гостя или заблокированного пользователя. Ответы с пользовательскими данными и CSRF имеют `Cache-Control: no-store`.

| Метод и путь | Вход | Успешный ответ |
| --- | --- | --- |
| GET /auth/csrf | — | 200 `{csrfToken}`, CSRF cookie |
| POST /auth/login | `{email,password}` и CSRF | 200 `{user,createdAt}`, новая session cookie |
| POST /auth/logout | CSRF, допускает уже истёкшую сессию | 204, сессия инвалидирована |
| GET /auth/me | — | 200 User или null |
| GET /generations/quote | — | 200 GenerationQuote |
| POST /generations | GeneratePoemRequest и CSRF | 200 Generation, в том числе FAILED либо PROCESSING при повторе |
| GET /generations | `status?`, `limit?`, `cursor?` | 200 Page<Generation> |
| GET /generations/by-request/{requestId} | UUID | 200 своя Generation |
| GET /generations/{id} | UUID | 200 своя Generation |
| GET /billing/wallet | — | 200 Wallet |
| GET /billing/transactions | `type?`, `from?`, `to?`, `limit?`, `cursor?` | 200 Page<WalletTransaction> |
| GET /billing/summary | `from?`, `to?` | 200 `{balance,credited,debited,refunded,netSpent}` |

Служебные `GET /health/live` и `GET /health/ready` расположены вне `/api/v1`, без авторизации, с минимальным JSON `{status}`. Admin доступен под `/admin/`; публичных endpoints для начисления и создания пользователя нет.

### Объекты ответа

| Объект | Обязательные поля |
| --- | --- |
| User | `id, email, displayName, createdAt` |
| Wallet | `id, userId, balance` |
| GenerationQuote | `cost, balance, balanceAfter, canGenerate`; balanceAfter = balance − cost, может быть отрицательным только в quote; canGenerate = balance >= cost |
| GeneratePoemRequest | `requestId, topic, instructions, mood, stanzaCount` |
| Generation | `id, userId`, все поля запроса, `result, status, cost, errorMessage, createdAt, startedAt, completedAt`; nullable только result/errorMessage/completedAt, startedAt у принятой записи всегда заполнен |
| WalletTransaction | `id, walletId, userId, type, amount, balanceAfter, description, createdAt`; `generationId` только у DEBIT/REFUND, у CREDIT поле отсутствует |
| Page<T> | `{items: T[], nextCursor: string|null}` |

Provider/model/tokens, внутренние error details, actor и административные флаги не передаются в пользовательском API. `createdAt` в ответе login — время создания сессии. Поля `sessionId` в HTTP-ответе нет.

История генераций сортируется по `(created_at DESC, id DESC)`, журнал — по `sequence DESC`. Cursor непрозрачный, подписанный, привязан к пользователю и фильтрам; неверный/чужой cursor даёт 400. Новые записи не должны дублировать элементы при переходе между страницами; первая страница обновляется отдельно. Срез не является снимком состояния: статус может измениться между страницами. Даты фильтра — RFC 3339 с timezone; интервал `[from,to)`, пропущенная граница не ограничивает период, `from >= to` даёт 400. Неизвестный статус/тип/параметр — 400.

Summary: `credited = SUM(CREDIT)`, `debited = -SUM(DEBIT)`, `refunded = SUM(REFUND)`, `netSpent = debited - refunded`; в период возврата netSpent может быть отрицательным. `balance` всегда текущий за всё время. Итоги считаются сервером независимо от пагинации, фильтр типа операций к summary не применяется.

### Ошибки и исход генерации

Единая форма API-ошибки: `{"error":{"code":"VALIDATION_ERROR","message":"Проверьте параметры","fields":{"topic":["Обязательное поле"]}},"requestId":"correlation-id"}`. `fields` необязателен; верхний requestId — идентификатор HTTP-обращения, не ключ генерации. Он также возвращается в `X-Request-ID`. Сообщения человеку — на русском; коды стабильны.

| HTTP | Коды/условия |
| --- | --- |
| 400 | `VALIDATION_ERROR`, `INVALID_CURSOR`, некорректный JSON |
| 401 | `AUTH_REQUIRED`, `INVALID_CREDENTIALS`; неверный email и пароль не различаются |
| 403 | `CSRF_FAILED`, `PERMISSION_DENIED` |
| 404 | `NOT_FOUND` для отсутствующего/чужого объекта |
| 409 | `INSUFFICIENT_FUNDS`, `IDEMPOTENCY_CONFLICT`, `BALANCE_LIMIT` |
| 413 / 415 | `PAYLOAD_TOO_LARGE` / `UNSUPPORTED_MEDIA_TYPE` |
| 429 | `RATE_LIMITED` или `CAPACITY_LIMIT`, Retry-After в секундах |
| 500 / 503 | `INTERNAL_ERROR` / `SERVICE_UNAVAILABLE`, без traceback и секретов |

Отказ/таймаут AI после принятия запроса — HTTP 200 с `status=FAILED`, если FAILED и REFUND записаны. Это завершённая бизнес-операция, которую UI обязан показать как ошибку с возвратом. При неподтверждённой записи возвращается 503 и инструкция проверить состояние. На уровне reverse proxy допустим инфраструктурный 502/504 без JSON; клиент трактует его как неизвестный исход, сохраняет ключ и восстанавливает состояние.

При действующей CSRF-защите отсутствие/неверность CSRF может дать 403 раньше проверки сессии. Тест 401 для POST должен передавать валидный CSRF. Login/logout защищены также для анонимного запроса.

## Контракт AI

Реальный адаптер отправляет один запрос с заданными моделью, лимитом выходных токенов и timeout. System prompt версионируется и отделён от пользовательских данных. Тема, пожелания, настроение и число строф передаются как данные; модель не получает пароли, email, баланс, ключи или доступ к инструментам.

Ожидаемый результат — русский стихотворный текст без заголовка, пояснений и Markdown-ограждений: ровно stanzaCount строф, разделённых пустой строкой, по 4 непустые строки. Нормализуются переводы строк и внешние пробелы. Детерминированный валидатор проверяет структуру и предел размера. Неверная структура, пустой/неразбираемый ответ, отказ модели, превышение лимита, HTTP 4xx/5xx и сетевой timeout дают FAILED с возвратом. Автоматический вызов для исправления результата запрещён.

Техническая приёмка структуры не доказывает художественное качество. Реальный прогон оценивается отдельно по теме, пожеланиям, настроению и связности в `acceptance.md`. Usage хранится только в сообщённых полях, не выдумывается из длины текста. Известные значения — неотрицательные целые; некорректный usage не портит валидный стих, такие поля становятся NULL с диагностическим событием. total_tokens не вычисляется вместо отсутствующего значения.

## Обязательные изменения frontend

`src/api/types.ts` и `src/api/http.ts` должны принять login без sessionId, получение/обновление CSRF, поиск по requestId, постраничные списки и серверные итоги. Local API адаптируется к общему интерфейсу и сохраняет отдельный демонстрационный режим. Автоматического fallback на local при ошибке backend нет.

Перед POST frontend сохраняет requestId и нормализованные параметры незавершённой операции в хранилище, ограниченном пользователем, без credentials. После перезагрузки сначала читает состояние по ключу. PROCESSING опрашивается каждые 2 секунды до финального состояния; после 120 секунд непрерывного ожидания автоматический polling прекращается, показывается «Проверить состояние». При 404 после обрыва допускается повтор прежнего POST с прежними параметрами; новый ключ возможен только для новой операции. При 401 polling прекращается, пользователь возвращается ко входу; после входа в тот же аккаунт восстановление продолжается. Logout удаляет локальные pending-данные и очищает React Query cache.

Повтор уже принятой операции не блокируется текущим quote.canGenerate. Смена полей формы не меняет ключ операции с неизвестным исходом. После подтверждённой финализации обновляются кошелёк, quote, журнал, summary и история. В HTTP-режиме нет демо-кнопок, демо-credentials и утверждений о генерации из заготовок. Текст стихотворения выводится безопасно, без исполнения HTML.

## Определение готовности

Результат готов, когда все BAC из `acceptance.md` имеют PASS с проверяемым доказательством, поставка из `plan.md` присутствует, чистый запуск по инструкции воспроизводим и HTTP-интерфейс работает с настоящим backend. Проверки реального AI и эксплуатационной среды могут иметь статус BLOCKED при отсутствии внешних условий; это означает частичную, а не полную приёмку. Обнаруженное нарушение доступа, двойное списание/возврат, рассогласование журнала, утечка секрета или потеря данных блокирует сдачу.
