# Как устроен проект

В текущей версии нет отдельных слоёв Domain/Application/Infrastructure, портов и классов адаптеров. Это обычное React-приложение с одним объектом API и двумя его реализациями: локальной и HTTP.

## С чего начать чтение

1. **src/api/local.ts** — все действия эмуляции. Найдите `generate`: здесь проверяются параметры и баланс, создаются запись и списание, сохраняются данные и запускается таймер. В том же файле находятся вход, выход, получение истории, завершение и возврат.
2. **src/api/storage.ts** — только загрузка/сохранение JSON: `read()` возвращает копию состояния, `save(state)` записывает его одним setItem. Неуспешная запись не меняет сохранённое состояние в памяти. Здесь же загрузка старой схемы.
3. **src/api/demo-data.ts** — два демо-аккаунта, готовая история и тексты стихотворений. `makePoem` — обычная функция, не отдельный AI-провайдер.
4. **src/api/types.ts** — формы данных и один небольшой интерфейс Api, который используют страницы.
5. **src/api/http.ts** — те же методы через fetch. Сюда нужно смотреть только при подключении backend. Запросы, ошибки и проверка ответов находятся в одном файле.
6. **src/api/index.ts** — читает конфигурацию и выбирает local/http.

## Вызов из React

```tsx
const api = useApi();

// Список и баланс
const poems = await api.getGenerations();
const wallet = await api.getWallet();

// Запуск. Цена не передаётся из интерфейса.
const generation = await api.generate({
  requestId: crypto.randomUUID(),
  topic: "Тихий вечер",
  instructions: "",
  mood: "neutral",
  stanzaCount: 2,
});
```

React Context хранит единственный объект api, созданный в main.tsx до рендера. TanStack Query отвечает только за загрузку, ошибки, кэш и повторное чтение статусов. Ни в Context, ни в hooks нет списаний и возвратов.

## Путь генерации

В `local.ts` метод `generate` выполняет обычную последовательность:

1. Прочитать состояние и найти текущего пользователя.
2. Проверить тему, настроение, количество строф и requestId. Если запрос уже принят, вернуть ту же запись без повторного списания.
3. Создать PENDING, проверить доступный баланс и добавить DEBIT на 10 единиц.
4. Одним `store.save(state)` сохранить и генерацию, и кошелёк, и операцию.
5. `processGeneration` меняет статус на PROCESSING и запускает следующий таймер.
6. `finishGeneration` сохраняет текст либо вызывает `refund`, которая создаёт FAILED и однократный REFUND.

Таймеры принадлежат экземпляру API. `dispose()` их останавливает — это используется тестами для имитации закрытия страницы. При следующем старте незавершённые записи получают FAILED с компенсацией. Если сохранить результат не удалось, чтение незавершённой записи возвращает ошибку хранения; после устранения проблемы перезагрузка выполняет компенсацию.

## Структура остальных файлов

```text
src/
  api/             # вся эмуляция и будущие HTTP-запросы
  pages/           # LoginPage, Dashboard, GenerationPages, BillingPage
  hooks/useData.ts # чтение данных и синхронизация баланса после генерации
  app/             # маршруты и React providers
  shared/          # UI, форматирование, ошибки, сумма операций
  tests/           # бизнес-сценарии и HTTP-проверки
```

`api.demo` содержит только три локальных тестовых переключателя: setDelay, failNext, reset. Панели Demo Tools нет; отдельного сервиса переключения аккаунтов тоже нет — используется обычный login. HTTP-реализация не содержит demo и не обращается к LocalStorage.

## Что сохранено при упрощении

Ключ `mini-kadrika:db`, схема v2, миграция v1, сессии, балансы и история не изменились. Изоляция пользователей проверяется в local.ts, принадлежность записи по ID — там же. Связанные изменения сохраняются единым снимком. Это по-прежнему демонстрация одной вкладки, а не ACID или настоящая конкурентная многопользовательская система.

REST-маршруты остались прежними. Для подключения backend достаточно реализовать согласованные контракты и выбрать VITE_DATA_SOURCE=http; переписывать страницы не требуется. Реальная интеграция ещё не тестировалась.
