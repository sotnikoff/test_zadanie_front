## Бизнес-цели, роли и объём

Цель — дать пользователю возможность получить стихотворение по заданным параметрам и видеть расход выданных единиц; владельцу — выдавать доступ, начислять единицы и контролировать их движение. Измеримые цели по аудитории, качеству и скорости пока отсутствуют (Q-04, Q-06).

| Роль | Возможности To-Be |
| --- | --- |
| Неавторизованный посетитель | Вход в выданный аккаунт; нет доступа к истории и биллингу. |
| Пользователь | Свои генерации, результаты, баланс и операции. |
| Владелец / уполномоченный оператор | Django Admin: управление доступом, начисления и просмотр данных в пределах Django permissions. Не отдельная роль в пользовательском DTO. |
| Технический администратор | Развёртывание, резервирование, запуск служебного восстановления; не новая продуктовая роль. |

Предлагаемый MVP: пользовательский кабинет из прототипа с реальным backend и одним AI-провайдером, операторские формы и простые итоги в Django Admin. Подтверждение объёма — Q-01.

As-Is: вход/выход, генерация из заготовок, фильтр истории по статусу, просмотр/копирование результата, баланс, журнал и чистый расход; локальное сохранение и демонстрационные возвраты. Нет настоящего AI, серверных прав, Django Admin, начислений через UI, БД и Docker Compose. Детали реализации — [архитектура](architecture.md).

## Функциональные требования

Все строки — кандидаты в MVP, статус **Draft**. «Прототип» в основании означает сценарий, а не согласие заказчика.

| FR-003 | Принимать тему, необязательные пожелания, настроение и число четверостиший; валидировать на сервере до списания. | Форма и `generate`; точные ограничения — BR-003. |
| FR-004 | До запуска показывать актуальную серверную цену, баланс и прогноз; повторно проверять баланс при принятии. | `getQuote`, форма; цена 10 предварительная. |
| FR-005 | Генерировать стихотворение через один внешний AI API, сохранять параметры и результат либо техническую ошибку. | Исходная задача; As-Is использует `makePoem`. |
| FR-006 | Однократно списывать цену принятой генерации; при окончательной технической неудаче однократно возвращать её. Недостаток средств не создаёт списания. | Прототип, исходная задача; транзакции — To-Be. |
| FR-007 | Повтор принятого запроса с тем же ключом возвращает ту же генерацию; иной набор параметров с тем же ключом отклоняется. После обрыва доступно чтение по `requestId`. | Дедупликация есть в API; поиск по ключу и сохранение ключа в UI отсутствуют. |
| FR-008 | Показывать собственную историю, статусы, параметры, даты и готовый текст; фильтровать по статусу и копировать текст. | `HistoryPage`, `DetailPage`, `CopyButton`. |
| FR-009 | Показывать баланс, неизменяемую историю начислений/списаний/возвратов, связи с генерациями, число завершённых стихов и чистый расход. | `Dashboard`, `BillingPage`, `summarize`. |
| FR-010 | Через Django Admin создавать аккаунт с нулевым кошельком, менять пароль, блокировать доступ; email уникален. | Предложение README; в прототипе нет. |
| FR-011 | Через Django Admin начислять положительные целые единицы с обязательным основанием, автором и защитой от повтора формы. | Предложение README; в прототипе нет. |
| FR-012 | Владельцу доступны фильтры по пользователю, периоду, статусу/типу; числовые итоги генераций, токенов и движения единиц без отдельного дашборда. | Предложение README; расчёты — BR-010, BR-011. |

## Нефункциональные требования

| ID | Проверяемое требование To-Be | Неопределённость |
| --- | --- | --- |
| NFR-001 | Серверная проверка сессии/прав на каждом защищённом запросе; Django password hashing, CSRF для изменяющих запросов, HttpOnly/Secure session cookie и HTTPS в рабочем окружении; AI-ключ только на сервере. | Срок сессии и процедура выдачи доступа — Q-02. |
| NFR-002 | Неотрицательный баланс, атомарные денежные изменения, уникальные списание/возврат и ключи запросов; проверка конкурентности на PostgreSQL. | Числовые ограничения — BR-004; не заменять тестами LocalStorage/SQLite. |
| NFR-003 | Внешний AI-вызов вне транзакций БД, с конечным тайм-аутом; после падения процесса возможна компенсация без повторного AI-вызова. | Пороги ожидания/восстановления — Q-05. |
| NFR-004 | Чистый запуск через Docker Compose, миграции и проверка сохранения данных после пересоздания контейнеров. | Хостинг и версии должны быть зафиксированы перед реализацией. |
| NFR-005 | Корреляция логов по `requestId`/`generationId`, причины сбоев и автор начисления; секреты и пароли не логируются. Резервная копия проверяется восстановлением. | Сроки хранения, RPO/RTO — Q-07. |
| NFR-006 | До приёмки согласовать нагрузку, лимит параллельных вызовов, p95 времени ответа и бюджет AI, затем измерить их на целевом окружении. | Чисел нет; 20 пользователей из README — гипотеза, не SLA. |
| NFR-007 | Состояния ожидания/ошибки/пустого списка понятны, повторная отправка блокируется; основные сценарии доступны с клавиатуры и на ширине 390 px. | Основано на прототипе; полная доступность пока не подтверждена. |

## Вне предлагаемого MVP

Реальные платежи, подписки, самостоятельная регистрация и самостоятельное восстановление пароля, редактор стихов, иные виды контента, социальные функции, отдельная административная SPA, графические BI-отчёты, очередь/брокер, микросервисы, WebSocket. Пользовательская отмена запущенной генерации и возврат «не понравилось» не определены и пока исключены (Q-03, Q-04).

Выбор демо-аккаунта, сброс LocalStorage, `demo.failNext`, начальные примеры и миграция демо v1 → v2 — инструменты прототипа, не продуктовые требования. Исправление ошибочных начислений не удалением истории упомянуто в README, но типы и права корректировки ещё не определены (Q-03); произвольное отрицательное начисление не предлагается.

## Принятые для проектирования допущения

| ID | Предварительное решение |
| --- | --- |
| A-01 | Один Django-монолит с Django Admin и PostgreSQL; один синхронный AI-вызов на принятую генерацию, без автоматических повторов внешнего вызова. |
| A-02 | Начальный баланс 0; положительное начисление оператором; цена 10 целых единиц независимо от длины, снимок цены в генерации. |
| A-03 | Cookie-сессия Django, SPA и API на одном origin; email — нормализованный уникальный логин. |
| A-04 | Статусы To-Be: `PROCESSING`, `COMPLETED`, `FAILED`. Технические ошибки/тайм-аут/восстановление компенсируются; терминальные состояния не переоткрываются. |
| A-05 | Служебная management command вручную завершает просроченные записи; нет автоматического продолжения после падения. Срок ключа равен сроку хранения записи. |
| A-06 | Финансовые записи не изменяются и не удаляются; аккаунты деактивируются. Правила удаления/обезличивания контента требуют решения. |

## Вопросы для согласования

Ответственный за бизнес-решения — заказчик/владелец; за технические параметры — разработчик совместно с владельцем хостинга. Сроки ответов пока не назначены.

| ID | Вопрос | Влияние / когда требуется ответ |
| --- | --- | --- |
| Q-01 | Подтверждаются ли пользовательские сценарии и FR-010–FR-013 в Django Admin? Кто будет оператором? | Граница реализации; до фиксации объёма MVP. |
| Q-02 | Как выдаются и восстанавливаются пароли, каков срок сессии и набор операторских прав? | Авторизация и административные формы; до реализации доступа. |
| Q-03 | Подтвердить 0/10, основание и лимиты начисления, права и правила исправления ошибочного начисления; нужны ли возврат по качеству и пользовательская отмена? | Финансовые правила и схема; до реализации биллинга. |
| Q-04 | Какой AI-провайдер/модель, допустимый контент и критерии качества, длины/рифмы? Считать ли пустой ответ технической ошибкой? | Предлагается пустой ответ компенсировать; до интеграции и контентной приёмки. |
| Q-05 | Каковы тайм-ауты AI/сервера/прокси, срок зависания и допустимая задержка ручной компенсации? Приемлемо ли отбрасывать поздний ответ после возврата? | Синхронный режим и восстановление; до интеграции. |
| Q-06 | Ожидаемая нагрузка, p95, лимиты запросов и бюджет AI? Нужна ли пагинация при ожидаемом объёме? | Ёмкость и API; до фиксации NFR и приёмки. |
| Q-07 | Сроки хранения контента/операций/ключей, удаление и выгрузка, RPO/RTO, хостинг? | Эксплуатация; до выпуска, а удаление — до фиксации схемы. |
| Q-08 | Часовой пояс и точный набор итогов владельца; достаточно ли списков Django Admin? | Отчётность; до реализации FR-012. |

Начать техническую подготовку можно на этих допущениях. Фиксировать реализацию backend как согласованный MVP пока нельзя: открыты Q-01–Q-05 и изменения [API](architecture.md). Полная OpenAPI-спецификация и план реализации — последующий шаг, не результат текущего задания. Проверки и доказательства собраны в [критериях приёмки](acceptance-criteria.md).
