# Мини-Кадрика

Интерактивный прототип сервиса создания стихотворений. Он помогает согласовать пользовательские сценарии, правила списания внутренних единиц и границы MVP перед разработкой backend.

## Как запустить

Установите Node.js 24 и выполните в папке проекта:

```sh
npm ci
cp .env.example .env
npm run dev
```

Откройте [localhost:5173](http://localhost:5173). Если порт занят, используйте адрес из терминала. Для демонстрации сервер и API-ключи не нужны.

## Тестовые пользователи

На странице входа выберите аккаунт и нажмите «Войти». Пароль для всех — `demo1234`.

| Пользователь | Email | Начальный баланс |
| --- | --- | ---: |
| Анна | user@example.com | 130 |
| Михаил | user2@example.com | 10 |
| Алексей | user3@example.com | 0 |

Кнопка **«Сбросить демо-данные»** на странице входа после подтверждения удаляет изменения всех аккаунтов и восстанавливает начальные балансы и историю. У Анны и Михаила есть примеры генераций; у Алексея история пустая. Обычное обновление страницы данные сохраняет.

## Что реализовано в прототипе

Пользователь входит в готовый аккаунт, создаёт стихотворение, копирует результат, просматривает свою историю, баланс и операции. Стоимость генерации — **10 единиц**. Перед запуском показаны цена, баланс и ожидаемый остаток. При недостатке единиц запуск недоступен; при сбое предусмотрен возврат.

Тема обязательна, пожелания необязательны. Доступны шесть настроений и от одного до четырёх четверостиший. Локальная генерация выполняется сразу, без искусственных задержек.

В прототипе пока нет backend, административного раздела, создания пользователей, начисления единиц и реального AI. Ниже описан следующий этап — работающий многопользовательский MVP. Реальные платежи, самостоятельная регистрация, подписки, редактор стихов и генерация других видов контента остаются за его пределами.

## Сценарии прототипа и критерии приёмки

| Сценарий | Условия и действия | Ожидаемый результат |
| --- | --- | --- |
| Вход | Ввести данные тестового аккаунта | Открывается главная, виден баланс пользователя. После обновления страницы сессия сохраняется. |
| Ошибка входа | Ввести неверный пароль | Появляется сообщение об ошибке; вход не выполнен. |

| Сбой генерации | Имитировать ошибку через тестовый API | Сохраняются статус ошибки, списание и один возврат. Итоговый баланс не меняется. В интерфейсе нет кнопки вызова сбоя; пример есть в начальной истории Анны. |
| История и копирование | Открыть историю, выбрать статус и готовое стихотворение, нажать «Скопировать» | Видны подходящие записи, параметры и текст выбранного результата. При разрешённом доступе к буферу текст копируется. |
| Баланс и операции | Открыть раздел «Баланс» после генерации | Показаны текущий остаток и операция −10 со ссылкой на результат. История операций недоступна для редактирования. |
| Сохранение данных | Создать стихотворение и обновить страницу | Результат, списание и новый баланс сохраняются. |
| Выход и смена пользователя | Выйти через меню профиля и войти другим аккаунтом | Открываются данные другого пользователя. Чужой результат по прямой ссылке недоступен; без входа защищённые страницы перенаправляют на логин. |
| Сброс демо | Выйти, нажать «Сбросить демо-данные» и подтвердить | Новые генерации удалены, балансы восстановлены до 130 / 10 / 0. Отмена подтверждения сохраняет изменения. |

## Демонстрация за 5–10 минут

1. На странице входа сбросить демо-данные, чтобы начать с известного состояния.
2. Войти Анной. Показать главную, баланс 130 и примеры стихотворений.
3. Создать стихотворение на тему «Первый снег», выбрать настроение и две строфы. Показать результат и баланс 120; скопировать текст.
4. Открыть историю и баланс: найти новую запись и списание −10. Обновить страницу и показать, что данные сохранились.
5. Открыть начальную неуспешную генерацию Анны и связанный возврат в журнале операций.
6. Выйти и войти Михаилом. Создать одно стихотворение: баланс меняется с 10 на 0, следующая генерация недоступна.
7. Войти Алексеем. Показать пустую историю и запрет генерации при нулевом балансе.
8. Выйти, сбросить демо-данные и снова войти Анной: баланс 130, созданного на показе стихотворения нет.

## Следующий этап: MVP на Django

Backend будем разрабатывать на **Django и Django REST Framework**, данные хранить в **PostgreSQL**. Существующий React-интерфейс подключим к REST API. **Django Admin** станет рабочим местом оператора для создания пользователей, начисления внутренних денежных единиц и просмотра базовой аналитики. Эти возможности запланированы, в текущем прототипе их ещё нет.

Django выбран, чтобы использовать встроенные средства управления пользователями, правами и административными страницами. Отдельный административный интерфейс на React разрабатывать не будем. Реальные платежи не подключаем: под начислением понимается выдача внутренних единиц оператором.

### Сценарии оператора и критерии приёмки

| Сценарий в Django Admin | Ожидаемый результат |
| --- | --- |
| Создать пользователя | Оператор указывает email, имя и начальный пароль. Создаются аккаунт и кошелёк с балансом 0. Повторный email отклоняется. Пользователь может войти в свой кабинет. |
| Управлять доступом | Оператор может сменить пароль и заблокировать аккаунт. Заблокированный пользователь теряет доступ к защищённым действиям, включая уже открытую сессию. |
| Начислить единицы | Оператор выбирает пользователя, вводит положительную целую сумму и обязательный комментарий. Баланс увеличивается, создаётся операция с автором, временем и остатком после начисления. Повторная отправка той же формы не дублирует начисление. |
| Проверить генерации | Доступны фильтры по пользователю, периоду и статусу; можно открыть параметры, результат или причину ошибки. |
| Проверить операции | Видны начисления, списания и возвраты, их основания и связанные генерации. Операции нельзя редактировать или удалять; баланс напрямую не редактируется. |
| Проверить права | Обычный пользователь не имеет доступа к админке и чужим данным. Операторские действия доступны только сотрудникам с соответствующими разрешениями. |

Начисление, списание и возврат будут выполняться через общую серверную логику. Кошелёк и запись операции изменяются в одной транзакции. Исправление суммы оформляется отдельной корректирующей операцией с основанием; история сохраняется.

### Базовая аналитика в админке

Сценарий: оператор выбирает период и, при необходимости, конкретного пользователя, затем видит списки и краткие числовые итоги над ними. Реализуем их как небольшое дополнение к страницам Django Admin, без отдельного дашборда и графиков.

- В генерациях: количество созданных за период запросов, разбивка по текущим статусам и число пользователей, запускавших генерации.
- В операциях: суммы начислений, списаний и возвратов за период; чистый расход — списания минус возвраты, без учёта начислений.
- В пользователях: текущий баланс каждого аккаунта и переходы к его генерациям и операциям. Баланс показывается на текущий момент, независимо от выбранного периода отчёта.

Критерий приёмки: итоги совпадают с записями при тех же фильтрах. Для генераций период определяется датой создания запроса, для операций — датой операции; часовой пояс указывается в интерфейсе. Возврат, выполненный в другом периоде, учитывается по собственной дате. При отсутствии записей показываются нулевые итоги. Это статистика внутренних единиц, а не отчёт о выручке или прибыли.

### Архитектура и надёжность

Один Django-проект с модулями пользователей, генераций и учёта единиц. API и админка используют общую прикладную логику. Для генерации в MVP будем использовать **OpenAI-совместимый HTTP API** одного выбранного провайдера. Адрес API, модель и ключ задаются на сервере. Совместимость нужных методов и параметров проверим при интеграции; использование именно сервиса OpenAI не обязательно.

**В MVP генерация выполняется синхронно в рамках одного HTTP-запроса:** браузер отправляет параметры в Django, backend обращается к AI и возвращает готовое стихотворение либо ошибку. Пока запрос выполняется, интерфейс показывает ожидание и блокирует повторную отправку. Это упрощение принято для скорости разработки первой рабочей версии; очереди и фонового обработчика в MVP не будет.

Сервер проверяет параметры и баланс, сохраняет генерацию и списание в одной короткой транзакции. Вызов AI выполняется вне транзакции базы, без удержания блокировки кошелька. После ответа сохраняется результат либо окончательная ошибка с однократным возвратом. Идентификатор запроса защищает от повторного списания.

Время ожидания ограничим и согласуем с таймаутами сервера и прокси. Потеря соединения с браузером сама по себе не означает ошибку AI: перед повтором интерфейс проверяет сохранённое состояние по идентификатору запроса. После аварийной остановки сервера зависшие записи потребуют проверки и завершения с однократной компенсацией через служебную операцию. Автоматическое продолжение генерации после остановки процесса в синхронном MVP не гарантируется.

**Дальнейшее развитие:** вынести вызов AI в фоновую задачу. Backend будет сразу возвращать идентификатор принятой генерации, отдельный обработчик — выполнять запрос и сохранять результат, а интерфейс — получать статус через API. На этом этапе добавим автоматическое восстановление задач, управляемые повторы и ограничения параллельной обработки. Выбор очереди и дополнительные трудозатраты оценим отдельно.

Для приёмки синхронного MVP проверим: получение результата в ответе на запрос, обработку ошибки и таймаута провайдера, невозможность отрицательного баланса при одновременных запросах, отсутствие повторных списаний и возвратов, серверную изоляцию пользователей и сохранность уже записанного результата. Отдельно проверим потерю соединения, повтор с тем же идентификатором и завершение зависшей записи с компенсацией после аварийного прерывания. Правила поздних ответов AI согласуем до интеграции. Перед запуском также проверим HTTPS, хранение секретов на сервере и восстановление базы из резервной копии.

### Подготовка к реализации после утверждения прототипа

После утверждения пользовательских сценариев проведём системный анализ и проектирование. К этому моменту основные функциональные требования уже будут собраны; на подготовительном этапе проверим их полноту, устраним противоречия и переведём в конкретные правила, модель данных и API-контракты.

Для MVP предлагается компактный комплект результатов: согласованные требования с критериями приёмки, схема БД с описанием полей, спецификация OpenAPI с примерами и план задач. Более подробное ТЗ имеет смысл готовить при появлении нескольких команд или дополнительных интеграций.

| Шаг | Что делаем | Результат |
| --- | --- | --- |
| 1. Уточнение функциональных требований | Проверяем сценарии пользователя и оператора, права, валидацию, начисления, списания, возвраты и расчёт аналитики. Разбираем ошибки и пограничные случаи. | Согласованный объём MVP и проверяемые критерии приёмки каждого сценария. |
| 2. Нефункциональные требования и ограничения | Согласуем число пользователей и параллельных генераций, допустимое время ответа, лимиты и бюджет AI, ограничения хостинга и синхронного запроса. Определяем требования к доступности, защите и срокам хранения данных, резервированию, допустимой потере данных и времени восстановления. | Измеримые требования: для каждого указаны целевое значение, условия и способ проверки. Неизвестные значения остаются открытыми вопросами, а не обещаниями. |
| 3. Системный анализ | Описываем взаимодействие React, Django, PostgreSQL и AI; состояния генерации и переходы между ними. Определяем границы транзакций, защиту от повторов, поведение при таймауте, обрыве соединения и позднем ответе провайдера. | Краткие схемы успешной генерации, ошибки с возвратом и начисления через админку; правила сохранения согласованного баланса. |
| 4. Проектирование БД | Описываем пользователей, кошельки, генерации и операции: связи, поля, типы, обязательность, уникальность, ограничения и индексы. Учитываем автора начисления, основания операций, фильтры аналитики и правила удаления данных. | ER-схема и словарь данных. Проверены один кошелёк на пользователя, неотрицательный баланс, уникальность запроса и отсутствие повторного списания или возврата. Модели прототипа служат исходным материалом, схема PostgreSQL проектируется отдельно. |
| 5. Проектирование API | Определяем методы и URL, схемы запросов и ответов, авторизацию, права, валидацию, коды ошибок, фильтрацию и пагинацию. Для генерации фиксируем синхронный ответ, идентификатор запроса, получение его состояния после обрыва и правила повторной отправки. Операторские действия описываем как формы Django Admin; отдельные публичные endpoints для них добавляем только при необходимости. | Спецификация OpenAPI и примеры успешных и ошибочных ответов, согласованные с frontend. | 6. План реализации и проверки | Связываем требования с таблицами БД, API или действиями админки и будущими тестами. Разбиваем работу на задачи с зависимостями, уточняем трудозатраты и порядок демонстраций. | План разработки, перечень приёмочных проверок и уточнённая оценка. |

Схему БД и API будем уточнять совместно: обнаруженные несоответствия возвращаем в анализ. Перед основной реализацией проверим выбранный OpenAI-совместимый сервис небольшим интеграционным запросом, чтобы подтвердить формат ответа и совместимость с ограничениями синхронного MVP.

**Готовность к разработке:** зафиксированы границы MVP и критерии приёмки; согласованы критичные правила учёта единиц, доступа и обработки сбоев; подготовлены схема БД и API-контракты; определены проверяемые нефункциональные требования и зависимости задач. Оставшиеся некритичные вопросы записаны с ответственными и сроками решения. Подготовка входит в первый этап оценки ниже; при расширении требований оценка пересматривается до начала реализации.

Использование Django Admin для создания аккаунтов и начислений принято как направление следующего этапа. Ниже остаются вопросы о правилах работы; решения по ним нужно согласовать.

| Вопрос | Что требуется определить |

| Автотесты HTTP-слоя | Выбор режима, запросы и обработка ошибок с подставными ответами. Реальный backend не подключён. |
| Ручная проверка ранее | Вход, создание стихотворения, списание, сохранение результата после обновления и связанная операция. Работа списания также подтверждена заказчиком. |
| Перед передачей заказчику | Пройти маршрут демонстрации на финальной версии; отдельно проверить копирование, подтверждение и отмену сброса, клавиатурную навигацию и мобильную ширину. Полная ручная приёмка не зафиксирована. |
| После подключения backend | Проверить реальную интеграцию, серверные права доступа, одновременные запросы и согласованность списаний и возвратов. |

## Что прототип не позволяет проверить

Прототип не подтверждает серверную безопасность, корректность одновременных списаний, восстановление после сбоев сервера, качество и стоимость реального AI, производительность и резервное копирование. Работа оператора в Django Admin и полезность предложенной аналитики также потребуют проверки на следующем этапе. Тесты локальной эмуляции не заменяют эти проверки.

## Устройство и ограничения

Интерфейс написан на React и TypeScript. Локальная эмуляция и сохранение находятся в `src/api`; данные хранятся в LocalStorage браузера. Для показа используйте одну вкладку: аккаунты, авторизация и денежные операции демонстрационные, настоящая конкурентная работа пользователей не реализована. Пароли доступны владельцу браузера, единицы не являются деньгами.

Стихи собираются из готовых строф. Тема служит заголовком, пожелания сохраняются, но не интерпретируются. Локальные тесты не подтверждают безопасность и транзакционную целостность будущего backend.

Для подключения backend нужно актуализировать предварительные [API-контракты](docs/api-contracts.md) под синхронный ответ генерации, согласовать их и реализовать серверную авторизацию, генерацию и учёт единиц. Затем задать в `.env` значения `VITE_DATA_SOURCE=http` и `VITE_API_BASE_URL` с адресом сервера и перезапустить приложение. Сейчас по умолчанию используется `local`; реальная интеграция ещё не проверялась.
